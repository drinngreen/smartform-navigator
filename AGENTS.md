# Regole strutturali
- Multy private loads keep atomic movement/receipt creation but never recalculate or assert legacy physical stock; official stock reads dated private rows once, with pre-22/09 saves blocked. Why: legacy reconciliation compared incompatible ledgers and blocked valid private loads.
- Niyol lives inside MultyDev: its home is the Niyol tab of /mn/admin/dev-multyproget (hub card and /mn/admin/niyol redirect there); Niyol sub-pages stay on its own tenant; why: the user requires Niyol inside MultyDev, never as a separate desktop, and never on Multy data.
- New office FIR drafts initialize format and editable status atomically through initializeMNFIRCreation; why: a later reset previously erased the paper format and hid saving controls.
- Both FIR payload mappers serialize declared sites as producer.luogo_produzione using rentriLuogoProduzione (separate street, civico, CAP, municipality; municipality from its name, never from a shared CAP alone); persist site fields separately from the producer address and reject unresolved municipalities; why: notes, address fallback and CAP guessing changed the actual waste origin.
- The processing-load action is a first-level tab beside Impianto and opens OperazioniMagazzinoModule in load-only mode; why: reuse the existing preview, date guards and manual confirmation without a second inventory write path or a duplicated entry point.
- Processing-load fields are rendered by CaricoLavorazioneForm and serialized by caricoLavorazioneMetadata into existing register columns, with supplementary quantities in raw; why: preserve separate private notes and quantity units without new stock write paths or schema changes.

- Office FIR editors share ConfermaFormularioRegistro for explicit registration from fresh RENTRI detail and a separate confirmation; why: saving a draft must never substitute for inventory confirmation, and site/date guards must stay centralized.
- TypeScript uses bundler module resolution for Vite; why: node10 resolution is unsupported by the preview compiler.

- Gli invii RENTRI di agosto 2026 stanno in un dataset separato (inviiRentriAgostoVerificati.json) generato dal CSV "Verifica_Agosto_2026_Accettati_Con_ID_RENTRI" con ID e progressivi letti dal RENTRI; mai riutilizzare ID delle richieste HTTP 202. Il dataset è mostrato sia nel pannello Dev sia nella Console RENTRI (tab registri e invii), perché il preferito "Invii al RENTRI" apre la console.- Giacenze dopo il 21/09: GiacenzeDocumentaliModule somma in sola lettura le righe registro_generale con incide_giacenze=true e le cernite CONFERMATA; nessun trigger né scrittura (le giacenze cambiano solo per operazioni umane).

- DARK LEMON write tools live in supabase/functions/dark-lemon-mn/operativo.ts and require the last user message to contain "CONFERMO" server-side; why: no agent write may happen without explicit human confirmation.
- The unified RENTRI FIR view uses subject-wide GET reads and derives company roles from fiscal codes; why: include intermediary FIRs without mixing tenants or inferring signatures from submission receipts.
- RENTRI formulari list reads use data_emissione_da/data_emissione_a windows (leggiTutteLePagineFormulari); why: RENTRI ignores page/page_size (verified 09/10/2026), so one unfiltered call misses older FIRs.
- FIR emission and plant acceptance send data only; signatures happen in the RENTRI app until FIRMA_API_ATTIVA (src/lib/rentriFirma.ts) is enabled; why: no API signing credential yet, and register/stock change only after RENTRI confirms closure.
- FIR → giacenze Multy Impianto: a scarico with Multy as producer and a RENTRI luogo_produzione (cantiere) different from the Piscina plant goes to the register with incide_giacenze=false, and scarichi are registered only after reading the RENTRI detail (valutaCantiere / verificaCantierePrimaDiRegistrare in src/lib/rentriFirGiacenze.ts); why: the list endpoint has no luogo_produzione and waste produced at a site never enters plant stock.
- Multy Impianto cernite: availability is computed client-side from the official giacenze (21/09 snapshot + human movements, minimum from the cernita date onward) and dragon_create_cernita_atomic only enforces date > 21/09 for Multy; why: magazzino_giacenze/Dragon stock are frozen and no longer the source of truth.
- verificaNuoviMovimenti rejects a movement only if it brings a CER below zero or lowers an already-negative balance; why: carichi that improve a negative CER must always be allowed.
